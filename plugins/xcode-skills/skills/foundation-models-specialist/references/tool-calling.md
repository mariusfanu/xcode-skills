# Tool Calling

Tool calling gives the model the ability to call your code to incorporate up-to-date information like recent events and data from your app. Tools are a powerful option, but have important trade-offs:

- A model _chooses_ whether and when to call a tool. When the model _always_ needs a piece of app data, put it in the prompt directly: it's faster, cheaper, and more reliable.

Use tools when:

- You want to give the model agency over a decision
- The model _may_ need some data, depending on how the session progresses

Tools are also a vital part of building a workflow:

- You want the model to _choose when_ trigger some side effect in your app, such as a game event.
- You want the model to pause and present the user with a choice or information request: a tool is a great place to trigger UI since the model will wait for the tool to return.
- You want the model to spin up an independent sub-session. You can run a new `LanguageModelSession` with a different model _inside a tool body_ and original model will wait for the tool to return the result. Unlike `DynamicProfile` where multiple models share a continuous transcript, a session inside a tool is fully isolated.

## Build a `Tool`

Building a tool in this framework uses many `@Generable` types idioms, so make sure you've read `references/generable.md` first. A key difference is that with a generable type, you use the `@Generable` macro, whereas for a tool you implement the `Tool` protocol directly.

Define name, description, arguments and call body to implement a `Tool`:

```swift
struct FindHotels: Tool {
    // Helps the model identify the capability. Defaults to type name when not specified.
    let name = "findHotels"

    // Helps the model decide when to call it, when not to call it, and what to expect. Required.
    let description = "Finds hotels options that best match a given request"

    // These arguments are generated by the model when it calls the tool.
    @Generable
    struct HotelSearch {
        let nights: Int
        let rooms: Int
    }

    // Required. 
    func call(arguments: HotelSearch) async throws -> [String] {
        var hotelOptions: [String] = []
        // ... fetch actual hotel information from a database to fill options

        return hotelOptions
    }
}
```

`arguments` is arbitrary `ConvertibleFromGeneratedContent` types. Returns arbitrary `PromptRepresentable` types. Typically, `arguments` is a `Generable` struct, and `Output` can be `String`, any `Generable` type, or a prompt composed by content including strings and images.

```swift
func call(arguments: Arguments) async throws -> Prompt {
    Prompt {
        "Photo of the best matching hotel:"
        Attachment(photo)
    }
}
```

## Use a tool

Just like a generable, the framework converts a `Tool` type into JSON schema that's fed to the model, but unlike a generable, tools are set in the `LanguageModelSession` initializer. Under-the-hood, the JSON of the tools get appended to the `Instructions` sent to the model. You don't have to supply instructions, but many models work better if you give it a hint when to use the tool:

```swift
let hotelTool = FindHotels()

// Tools go before instructions
let sessionA = LanguageModelSession(
    tools: [hotelTool]) {
    """
    You are a friendly travel agent. \
    Use \(hotelTool.name) if the user needs help finding a place to stay.
    """
}

// No instructions
let sessionB = LanguageModelSession(tools: [hotelTool])
```

Be sure `hotelTool.name` (which is "findHotels") instead of referring to the type name.

Finally, you can actually hide a tool's schema in the `Instructions` by overriding `includesSchemaInInstructions`, but this is only recommended for advanced usage when you'll send the schema to the model some other way, since hiding the schema essentially hides the tool from the model:

```swift
struct MyTool: Tool {
    // ... other requirements
    var includesSchemaInInstructions: Bool { false }
}
```

## Trigger app side-effects

Tools can directly affect your app's UI or state, using a simple but powerful trick: for apps that use a View/ViewModel pattern or something similar you can pass a ViewModel directly in the initializer of the tool:

```swift
let flightTool = FlightTool(viewModel: flightsViewModel)
let sessionC = LanguageModelSession(tools: [hotelTool, flightTool])
```

You can pass almost in the tool initializer, but keep in mind the `Tool` protocol is `Sendable`. In the example below, `FlightsTool` is able to mutate app state via its `viewModel` of type `FlightsViewModel` because 1) `FlightsViewModel` is `@MainActor` isolated and 2) `FlightsTool` uses `await` to wait on the results from the `@MainActor` thread:

```swift
struct FlightsTool: Tool {
    let name = "findFlights"
    let description = "Look up flight options for given dates and locations"

    let viewModel: FlightsViewModel

    @Generable
    struct Arguments {
        let cityTo: String
        let cityFrom: String
        let travelerCount: Int
    }

    func call(arguments: Arguments) async throws -> String {
        // Pause for user confirmation of the cities the model inferred
        await viewModel.confirmDestination(from: arguments.cityFrom, to: arguments.cityTo)

        // Get the flights
        let flightList = await viewModel.lookupFlights(for: arguments.travelerCount)

        // Note FlightsViewModel looks up the flights, but the tool here should
        // remain responsible for formatting the results for the model, since
        // this is an important type of prompting
        return "Found these flights: \(flightList)"
    }
}

@Observable
@MainActor
class FlightsViewModel {
    // ... state that updates a view in the app
    var showConfirmation = false

    func confirmDestination(from: String, to: String) {
        // ... update some UI
    }

    func lookupFlights(for travelerCount: Int) -> [String] {
        // ... do a database lookup
        return ["Flight 123", "Flight 321"]
    }
}
```

> **Tip:** Tools that mutate state are a key building block of an AI workflow. You can go much further building complex workflows using tools + `DynamicProfile`.

## Advanced: Dynamic tools

When a tool’s schema needs to be runtime supplied, set `arguments` in the `call` function to `GeneratedContent`. Instead of writing a static `@Generable` arguments type, override the `Tool` protocol's `parameters` property:

```swift
struct SearchProductsTool: Tool {
    let name = "findProducts"
    let description = "Search inventory optionally filtered by category"

    // Override as a computed property
    var parameters: GenerationSchema {
        let categories: DynamicGenerationSchema

        // ... build a DynamicGenerationSchema with the available
        // categories for the part of the shop the user's looking at ...

        let arguments = try GenerationSchema(root: categories, dependencies: [])
        return arguments.generationSchema
    }

    func call(arguments: GeneratedContent) async throws -> [String] {
        var products: [String] = []
        // ... do actual search ...
        return products
    }
}
```

Read about how to build and compile a `DynamicGenerationSchema` in `references/generable.md`.
